# 从零开始学 React

## 1. Basic Understanding / 基本认识

### 1.1 What React Really Is / React 到底是什么

React is a library for building user interfaces. Its core idea is strikingly simple: you describe what the UI should look like for a given state, and React figures out how to update the DOM to match. You do not write instructions like "find the button with id `submit` and change its text." You write "here is a component; when `count` is 5, the button should say 'Clicked 5 times'." React handles the rest.

React 是一个构建用户界面的库。它的核心思想简单得出奇：你描述对于某个给定的状态 UI 应该长什么样，React 负责算出如何更新 DOM 来匹配。你不需要写“找到 id 为 `submit` 的按钮然后改文字”。你写的是“这是一个组件；当 `count` 为 5 时，按钮应显示 'Clicked 5 times'。”剩下的交给 React。

### 1.2 JSX: HTML in JavaScript Is a Lie / JSX：写在 JS 里的 HTML 是假象

The first thing that strikes every beginner is the weird mix of HTML and JavaScript in `.jsx` files. It looks like someone broke the rules of both languages. In truth, JSX is **syntactic sugar** for `React.createElement()`. The browser never sees JSX — it is compiled away during the build step (by Vite, in my blog project). Every `<div>...</div>` becomes a function call that returns a plain JavaScript object describing the element.

每个初学者首先感到诧异的就是 `.jsx` 文件里 HTML 和 JavaScript 的奇怪混合。它看起来像是有人同时打破了两门语言的规则。事实上，JSX 是 `React.createElement()` 的**语法糖**。浏览器永远不会看到 JSX——它在构建阶段（我博客项目里用的是 Vite）被编译掉了。每个 `<div>...</div>` 都变成一个函数调用，返回一个描述该元素的普通 JavaScript 对象。

```jsx
// These two are equivalent / 以下两者等价
const element = <h1 className="greeting">Hello</h1>;

const element = React.createElement("h1", { className: "greeting" }, "Hello");
```

This matters for one practical reason: JSX is not HTML. The attribute is `className`, not `class`. Self-closing tags like `<br>` must be written `<br/>`. JavaScript expressions live inside curly braces `{}`. These are not quirks — they follow from the fact that JSX compiles to JavaScript, and JavaScript has its own naming rules.

这一点有一个实际的重要性：JSX 不是 HTML。属性是 `className`，不是 `class`。自闭合标签如 `<br>` 必须写成 `<br/>`。JavaScript 表达式放在花括号 `{}` 里。这些不是怪癖——它们源于 JSX 编译为 JavaScript 这个事实，而 JavaScript 有自己的命名规则。

**How I actually learned this / 我实际上是怎么学会的：** I didn't read the JSX specification first. I copied code generated by an LLM, saw `className` where I expected `class`, got a compiler error when I changed it back, and learned the rule through the error message. When you learn React by vibing first and understanding later, compiler errors are your primary teacher. Every `Failed to compile` message is a lesson about what JSX is _not_.

我并不是先读了 JSX 规范。我复制了大模型生成的代码，在预期看到 `class` 的地方看到了 `className`，把它改回去后收到了编译错误，通过报错信息学到了这条规则。当你先 vibe 后理解来学习 React 时，编译错误是你的主要老师。每条 `Failed to compile` 消息都是关于 JSX *不是*什么的一课。

### 1.3 Components: The Only Abstraction That Matters / 组件：唯一重要的抽象

React revolves around a single idea: **everything is a component**. A component is a JavaScript function whose name starts with a capital letter. It returns JSX. That's it.

React 围绕着唯一的想法运转：**一切都是组件**。组件就是一个名字以大写字母开头的 JavaScript 函数，它返回 JSX。就这么多。

```jsx
function MyButton() {
  return <button>I am a button</button>;
}
```

Capitalization is how React distinguishes your components from native HTML elements. `<div>` is an HTML element — React passes it to the DOM. `<MyButton>` is your component — React calls the `MyButton` function and renders whatever JSX it returns. If you accidentally write `<mybutton>`, React will look for a native HTML element called `mybutton`, fail to find it, and silently render a meaningless DOM node. This rule is enforced by nothing but convention — miss it, and nothing works, but no one tells you why. I learned this the hard way when a component I wrote simply refused to appear on the page. The cause? A lowercase first letter.

大写字母是 React 区分你的组件和原生 HTML 元素的方式。`<div>` 是 HTML 元素——React 将其交给 DOM。`<MyButton>` 是你的组件——React 调用 `MyButton` 函数并渲染它返回的 JSX。如果你不小心写成 `<mybutton>`，React 会寻找一个叫 `mybutton` 的原生 HTML 元素，找不到，然后默默渲染一个无意义的 DOM 节点。这条规则没有任何机制强制执行——违反了它，什么都跑不通，但没人告诉你为什么。我是在一个我写的组件死活不出现在页面上时才深刻领教的。原因？首字母小写了。

**Why components?** Because composing UIs from reusable pieces is easier than managing one giant HTML file. When you write `<Header />`, `<Routes />`, `<Footer />` in `App.jsx` (as I did in my blog), each of those is a separate function in a separate file. Each has its own state, its own logic, its own CSS. They are the LEGO bricks of a React application. The entire architecture of a React project is the design of this component tree.

**为什么需要组件？** 因为从可复用的积木搭建 UI 比管理一个巨无霸 HTML 文件容易。当你在 `App.jsx` 里写 `<Header />`、`<Routes />`、`<Footer />`（就像我在博客里做的那样），每一个都是独立文件里的独立函数。每一个有自己的状态、自己的逻辑、自己的 CSS。它们是 React 应用的乐高积木。React 项目的整个架构就是这棵组件树的设计。

## 2. Quick Start / 快速入门

This section covers the five syntactic patterns that appear in nearly every React component you will ever write. None of them require deep understanding to use. When I started, I memorized them as incantations — and that worked fine. The understanding came later, retroactively, as I read my own code and realized why each rule existed.

这一节覆盖几乎所有 React 组件中都会出现的五种语法模式。它们都不需要深刻理解就能使用。我刚开始的时候把它们当咒语背——效果还不错。理解是后来反刍自己的代码时才到来的。

### 2.1 Single Root Element / 有且只有一个根元素

Every component must return a **single** root element. You cannot return two adjacent `<div>`s. If you try, the compiler will produce a cryptic error that mentions "JSX expressions must have one parent element."

每个组件必须返回**单一**根元素。你不能返回两个相邻的 `<div>`。如果你尝试，编译器会抛出一个晦涩的报错，提到"JSX 表达式必须有单个父元素"。

```jsx
// Wrong / 错误
return (
  <h1>Title</h1>
  <p>Content</p>
);

// Correct / 正确
return (
  <div>
    <h1>Title</h1>
    <p>Content</p>
  </div>
);
```

If the extra `<div>` would break your CSS layout, use a **fragment** — an invisible wrapper that produces no DOM node:

如果多余的 `<div>` 会破坏你的 CSS 布局，用 **fragment**——一个不产生 DOM 节点的隐形包裹：

```jsx
return (
  <>
    <h1>Title</h1>
    <p>Content</p>
  </>
);
```

The fragment `<>...</>` is syntactic sugar for `<React.Fragment>...</React.Fragment>`. It exists purely to satisfy the single-root rule without polluting the DOM.

Fragment `<>...</>` 是 `<React.Fragment>...</React.Fragment>` 的语法糖。它纯粹为了满足单根规则而存在，不污染 DOM。

**The real reason behind this rule.** JSX compiles to `React.createElement()`, and every function call must return a single value. `return` cannot return two things. The rule is not an arbitrary React limitation — it is a JavaScript constraint. This is one of those things that makes no sense until you understand the compilation step, and then becomes obvious.

**这条规则背后的真实原因。** JSX 编译为 `React.createElement()`，而每个函数调用必须返回单个值。`return` 不能返回两个东西。这条规则不是 React 的任意限制——它是 JavaScript 的约束。这是那种在你理解编译步骤之前毫无道理、理解之后显而易见的事情。

### 2.2 camelCase Attributes / 驼峰命名属性

JSX attributes follow JavaScript naming conventions, not HTML ones. `class` becomes `className`. `onclick` becomes `onClick`. `tabindex` becomes `tabIndex`. Multi-word attributes are all camelCased.

JSX 属性遵循 JavaScript 命名习惯，而非 HTML。`class` 变为 `className`。`onclick` 变为 `onClick`。`tabindex` 变为 `tabIndex`。多词属性全部驼峰命名。

```jsx
<input
  className="input-field"
  type="text"
  placeholder="Enter name"
  onChange={handleChange}
/>
```

**Why?** JSX compiles to JavaScript objects, and `class` is a reserved keyword in JavaScript. The compiler can't use it as a property name. The rule is a direct consequence of the JSX → `React.createElement()` compilation — every attribute becomes a property on a JavaScript object, and JavaScript property names follow JavaScript rules. Again, this feels arbitrary until you understand what JSX actually is. Then it feels inevitable.

**为什么？** JSX 编译为 JavaScript 对象，而 `class` 在 JavaScript 中是保留关键字。编译器不能将其用作属性名。这条规则是 JSX → `React.createElement()` 编译的直接后果——每个属性变成 JavaScript 对象的属性，而 JavaScript 属性名遵循 JavaScript 规则。同样，在你理解 JSX 真正是什么之前这感觉随意，理解之后感觉必然。

### 2.3 Interpolation: `{}` / 插值表达式

Curly braces `{}` in JSX escape back to JavaScript. Anything inside them is evaluated as a JavaScript expression. Variables, function calls, arithmetic — whatever produces a value.

JSX 中的花括号 `{}` 逃逸回 JavaScript。里面任何内容都作为 JavaScript 表达式求值。变量、函数调用、算术——任何产生值的东西。

```jsx
const name = "Joshua";
const element = <h1>Hello, {name}!</h1>; // <h1>Hello, Joshua!</h1>

const currentYear = new Date().getFullYear();
const footer = <footer>© {currentYear}</footer>;
```

You cannot put statements inside `{}`. `{if (x) { ... }}` will not work. You can only put expressions — things that produce a value. This limitation directly motivates the conditional rendering patterns in the next section.

你不能把语句放在 `{}` 里。`{if (x) { ... }}` 不会工作。你只能放表达式——产生值的东西。这个限制直接催生了下一节的条件渲染模式。

### 2.4 Conditional Rendering / 条件渲染

Since `{}` cannot contain `if` statements, conditional rendering uses three main patterns: ternary operators, logical `&&`, and extracting conditions into normal `if` statements outside the JSX.

既然 `{}` 不能包含 `if` 语句，条件渲染使用三种主要模式：三元运算符、逻辑 `&&`，以及将条件提取到 JSX 外部的普通 `if` 语句。

**Pattern 1: Ternary operator / 模式一：三元运算符**

```jsx
return <div>{isLoggedIn ? <AdminPanel /> : <LoginForm />}</div>;
```

**Pattern 2: Logical `&&` for "render or nothing" / 模式二：逻辑 `&&` 实现“有或无”**

```jsx
return (
  <div>
    {unreadMessages.length > 0 && <Badge count={unreadMessages.length} />}
  </div>
);
```

When the left side of `&&` is falsy, React renders nothing. This is the idiomatic way to conditionally show a component without an `else` branch. My blog's `PostPage` uses this extensively: `{validImages.length > 0 && ( ... )}` for the image section, `{replyTo && ( ... )}` for the reply indicator.

当 `&&` 左侧为假时，React 渲染空。这是条件显示组件而不带 `else` 分支的惯用方式。我博客的 `PostPage` 大量使用这个模式：图片区域用 `{validImages.length > 0 && ( ... )}`，回复指示器用 `{replyTo && ( ... )}`。

**Pattern 3: Extract to variable / 模式三：提取到变量**

```jsx
let content;
if (loading) {
  content = <Spinner />;
} else if (error) {
  content = <ErrorMessage message={error} />;
} else {
  content = <DataView data={data} />;
}
return <div>{content}</div>;
```

This pattern is cleaner when there are three or more branches. The `if/else` logic stays in plain JavaScript, and JSX only receives the final result.

当有三个或更多分支时，这种模式更整洁。`if/else` 逻辑留在普通 JavaScript 中，JSX 只接收最终结果。

### 2.5 Event Handling / 事件处理

React uses `on` + camelCase event names. You pass a function reference, not a function call.

React 使用 `on` + 驼峰事件名。你传递一个函数引用，而非函数调用。

```jsx
function MyButton() {
  function handleClick() {
    alert("Clicked!");
  }

  return <button onClick={handleClick}>Click me</button>;
}
```

The single most common beginner mistake is writing `onClick={handleClick()}` with parentheses. This calls the function _during rendering_, not when the button is clicked. The correct form passes the function itself, without calling it.

最常见的新手错误是写成 `onClick={handleClick()}` 带括号。这会在*渲染时*调用函数，而非在按钮被点击时。正确形式是传递函数本身，不调用它。

**How I learned this.** My generated code always had `onClick={handleClick}`. At some point I thought the parentheses were missing and added them — `onClick={handleClick()}`. The function ran on every render, causing an infinite loop of state updates and re-renders. The lesson: React's event system expects a function reference. When you add `()`, you're calling the function immediately and passing its _return value_ as the event handler, which is almost always wrong. This is a five-second mistake that teaches a lasting lesson.

**我怎么学会的。** 我生成的代码总是 `onClick={handleClick}`。某个时刻我觉得少了括号，加上了——`onClick={handleClick()}`。函数在每次渲染时运行，导致状态更新和重渲染的无限循环。教训：React 的事件系统期望一个函数引用。当你加上 `()`，你是在立刻调用函数并将其*返回值*作为事件处理器传递，而这几乎总是错误的。这是一个五秒钟犯下、却教了一辈子记住的错误。

### 2.6 A Mental Model / 一个心智模型

At this point, the five patterns above form a complete mental model for rendering static and interactive UIs in React. A component is a function that returns JSX. JSX uses `{}` for JavaScript expressions, ternary/`&&` for conditions, and `onEvent={handler}` for interactivity. The single-root rule is a compilation artifact. Everything else in React builds on these five foundations — `useState` extends them with state, `useEffect` extends them with side effects, and `useContext` extends them with shared data. But syntactically, every React component you will ever write is composed from these same building blocks.

至此，以上五种模式构成了在 React 中渲染静态和交互 UI 的完整心智模型。组件是返回 JSX 的函数。JSX 用 `{}` 写 JavaScript 表达式，用三元/`&&` 写条件，用 `onEvent={handler}` 写交互。单根规则是编译产物。React 中其他一切构建在这五个基础之上——`useState` 用状态扩展它们，`useEffect` 用副作用扩展它们，`useContext` 用共享数据扩展它们。但语法上，你将写的每一个 React 组件都由这些相同的积木组成。

## 3. Component State: useState / 组件状态：useState

### 3.1 Why Variables Are Not Enough / 为什么普通变量不够

A naive attempt at adding interactivity to a React component might look like this. Declare a variable. Change it in an event handler. Expect the UI to update.

给 React 组件添加交互性的一次天真尝试可能长这样。声明一个变量。在事件处理器里改变它。预期 UI 会更新。

```jsx
function Counter() {
  let count = 0;

  function handleClick() {
    count = count + 1;
    console.log(count); // logs the new value
  }

  return <button onClick={handleClick}>Clicked {count} times</button>;
}
```

Click the button. The console prints `1`, then `2`, then `3`. The variable updates correctly. But the button still displays `Clicked 0 times`. React never re-renders the component. It has no way of knowing that `count` changed, because `count` is just a local variable — JavaScript variables do not notify React when they are reassigned.

点击按钮。控制台打印 `1`，然后 `2`，然后 `3`。变量正确更新了。但按钮仍然显示 `Clicked 0 times`。React 从不重新渲染组件。它无从知道 `count` 改变了，因为 `count` 只是一个局部变量——JavaScript 变量在重新赋值时不会通知 React。

This is the core problem `useState` solves: React must be told when data changes, so it can re-render the components that depend on that data. State is data that, when updated, triggers a re-render.

这正是 `useState` 解决的核心问题：React 必须被告知数据何时改变，这样它才能重新渲染依赖那些数据的组件。状态是那种一旦更新就会触发重渲染的数据。

### 3.2 The useState Hook / useState 钩子

`useState` is a function imported from `react`. It takes one argument — the initial value — and returns an array with exactly two items: the current state value, and a function to update it. Array destructuring is the universal convention for naming these two items.

`useState` 是从 `react` 导入的一个函数。它接受一个参数——初始值——并返回一个恰好包含两项的数组：当前状态值，以及一个更新它的函数。数组解构是命名这两项的通用惯例。

```jsx
import { useState } from "react";

function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);
  }

  return <button onClick={handleClick}>Clicked {count} times</button>;
}
```

Every call to `setCount` with a new value schedules a re-render of the component. React re-executes the function body, calls `useState(0)` again, but this time returns the _updated_ value — the one that was passed to `setCount`. The `0` is only used on the very first render. On subsequent renders, `useState` returns the current state. This is why the component always reflects the latest state: each render gets a fresh snapshot of the current value.

每次用新值调用 `setCount` 都会安排一次组件的重渲染。React 重新执行函数体，再次调用 `useState(0)`，但这次返回*更新后的*值——也就是传给 `setCount` 的那个。`0` 只在第一次渲染时使用。在后续渲染中，`useState` 返回当前状态。这就是为什么组件总是反映最新状态：每次渲染都获得当前值的一个新快照。

### 3.3 State Is a Snapshot / 状态是一个快照

A critical subtlety that confused me for a long time: `setCount` does _not_ change the variable `count` immediately. `count` is a `const`. It cannot be reassigned. Instead, `setCount` schedules a re-render with the new value. The `count` variable in the current render still holds the old value.

一个困扰了我很久的关键微妙之处：`setCount` *不*会立即改变变量 `count`。`count` 是一个 `const`。它不能被重新赋值。相反，`setCount` 用新值安排一次重渲染。当前渲染中的 `count` 变量仍然持有旧值。

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);
    console.log(count); // Still logs the old value!
  }

  return <button onClick={handleClick}>Clicked {count} times</button>;
}
```

After `setCount(count + 1)`, `count` is still `0`. The `console.log` proves it. The update only takes effect in the _next_ render, when the component function is called again with the new state value. React batches multiple state updates within the same event handler into a single re-render, which is a performance optimization. This means you should never rely on the current value of a state variable immediately after calling its setter. If you need to compute the next state based on the previous state, use the **functional update** form.

在 `setCount(count + 1)` 之后，`count` 仍然是 `0`。`console.log` 证实了这点。更新只在*下一次*渲染中生效，那时组件函数会带着新状态值再次被调用。React 将同一事件处理器中的多次状态更新批处理为一次重渲染，这是一项性能优化。这意味着你绝对不应在调用 setter 后立刻依赖状态变量的当前值。如果你需要基于前一个状态计算下一个状态，使用**函数式更新**形式。

### 3.4 Functional Updates / 函数式更新

When the new state depends on the previous state, pass a function to the setter instead of a value. The function receives the guaranteed-latest previous state and returns the new state.

当新状态依赖于前一个状态时，向 setter 传递一个函数而不是一个值。该函数接收保证是最新的前一个状态，并返回新状态。

```jsx
// Risky when multiple updates are batched
// 多次更新被批处理时有风险
setCount(count + 1);
setCount(count + 1); // both use the same stale `count`

// Always correct
// 永远正确
setCount((prev) => prev + 1);
setCount((prev) => prev + 1); // each uses the updated previous value
```

This pattern is essential in any component where a single user action triggers multiple state updates that depend on one another, or where updates may be queued rapidly (like a fast double-click, or a character-by-character input in a text field). My blog's `handleLike` function could benefit from this — the comment count increment `setPost((prev) => prev ? { ...prev, comment_count: prev.comment_count + 1 } : prev)` is a defensive pattern that avoids stale closure bugs. I didn't know why I was writing it that way when the LLM first generated it. Now I do.

这个模式在任何单次用户操作触发多次相互依赖的状态更新，或更新可能快速入队（比如快速双击，或文本字段中逐字符输入）的组件中至关重要。我博客的 `handleLike` 函数就可以受益于此——评论计数自增 `setPost((prev) => prev ? { ...prev, comment_count: prev.comment_count + 1 } : prev)` 是一个防御性模式，避免闭包陷阱 bug。当大模型第一次生成它时我不知道为什么这样写。现在我知道了。

### 3.5 Working with Objects and Arrays / 对象和数组的操作

State in React should be treated as **immutable**. When you have an object or array in state, never mutate it directly. Always create a new copy and call the setter with the new copy. React compares state by reference — if you mutate the existing object and call `setState` with it, React sees the same reference and skips the re-render.

React 中的状态应被视为**不可变的**。当你的状态中有对象或数组时，绝不要直接修改它。始终创建一个新副本并用新副本调用 setter。React 通过引用比较状态——如果你修改了现有对象并用它调用 `setState`，React 看到相同的引用，会跳过重渲染。

```jsx
// Wrong — mutates the existing array
// 错误——修改了现有数组
const [items, setItems] = useState([]);
function addItem(item) {
  items.push(item);
  setItems(items); // same reference → no re-render
}

// Correct — creates a new array
// 正确——创建了新数组
function addItem(item) {
  setItems([...items, item]);
}
```

The spread operator `...` is the workhorse for creating shallow copies of objects and arrays in state updates. For deeply nested state, libraries like Immer exist, but for most components spread is enough.

展开运算符 `...` 是在状态更新中创建对象和数组浅拷贝的主力工具。对于深层嵌套状态，存在 Immer 等库，但对大多数组件来说展开就够了。

### 3.6 How I Learned useState / 我是怎么学会 useState 的

I did not learn `useState` by reading the documentation. I saw it in generated code — always the same pattern: `const [something, setSomething] = useState(initialValue)`. I copied it mechanically. The LLM wrote `setIsLiked`, `setComments`, `setPost` in my blog's `PostPage`, and I treated each as a required incantation: declare state with `useState`, update it with the setter. The deeper understanding — snapshots, batching, immutability — came later, usually after a bug. When I tried to `console.log` state immediately after setting it and saw the old value, I learned about snapshots. When I tried to `.push` into an array in state and the UI didn't update, I learned about immutability. When I wrote two consecutive `setCount(count + 1)` calls and the counter only went up by one, I learned about functional updates. React's design is opinionated, and those opinions surface as bugs when you violate them. Learning React is, in large part, learning the bug patterns and what they are trying to tell you.

我不是通过读文档学会 `useState` 的。我在生成的代码中看到它——总是同样的模式：`const [something, setSomething] = useState(initialValue)`。我机械地复制它。大模型在我博客的 `PostPage` 里写了 `setIsLiked`、`setComments`、`setPost`，我把每个都当成必要的咒语：用 `useState` 声明状态，用 setter 更新它。更深刻的理解——快照、批处理、不可变性——是后来才来的，通常是在一个 bug 之后。当我试图在设置状态后立刻 `console.log` 状态并看到旧值时，我学到了快照。当我试图对状态中的数组 `.push` 而 UI 不更新时，我学到了不可变性。当我写了两个连续的 `setCount(count + 1)` 而计数器只加了一次时，我学到了函数式更新。React 的设计是带有强烈观点的，那些观点在你违反它们时以 bug 的形式浮现出来。学 React，很大程度上就是学习 bug 模式以及它们试图告诉你什么。

## 4. Component Communication: Props / 组件通信：Props

### 4.1 The Problem: Components Are Isolated / 问题：组件是孤立的

After building a few components with their own `useState`, a natural question arises. A button component manages its own click count. A form input manages its own text. But what if two components need to share data? What if a parent component needs to pass information down to a child? React components are isolated functions — they do not share local variables. If `Parent` has a piece of data and `Child` needs to display it, `Child` cannot reach into `Parent`'s scope to read the variable. There must be an explicit data-passing mechanism. That mechanism is **props**.

在构建了几个各自带着 `useState` 的组件之后，一个自然的问题浮现出来。按钮组件管理自己的点击计数。表单输入管理自己的文本。但如果两个组件需要共享数据呢？如果父组件需要把信息向下传递给子组件呢？React 组件是孤立的函数——它们不共享局部变量。如果 `Parent` 有一份数据而 `Child` 需要显示它，`Child` 不能伸手进 `Parent` 的作用域去读变量。必须有一个显式的数据传递机制。这个机制就是 **props**。

### 4.2 Props Are Function Arguments / Props 就是函数参数

In plain JavaScript, if one function needs data from another, you pass it as an argument. React components are functions, so they receive data the same way. A single argument — conventionally named `props` — holds everything the parent passes down.

在普通 JavaScript 中，如果一个函数需要另一个函数的数据，你把它作为参数传递。React 组件就是函数，所以它们以相同的方式接收数据。一个单一参数——按惯例命名为 `props`——持有父组件传递下来的一切。

```jsx
// Parent passes data to Child like HTML attributes
// 父组件像写 HTML 属性一样向子组件传递数据
function Parent() {
  const name = "Joshua";
  return <Child name={name} age={20} />;
}

// Child receives it as a single object
// 子组件将其作为单个对象接收
function Child(props) {
  return (
    <p>
      {props.name} is {props.age} years old.
    </p>
  );
}
```

Every attribute on the JSX tag becomes a property on the `props` object. `name={name}` becomes `props.name`. `age={20}` becomes `props.age`. Props are read-only — a child component must never reassign `props.anything`. The data flows one way: from parent to child, never the reverse.

JSX 标签上的每个属性都变成 `props` 对象上的一个属性。`name={name}` 变成 `props.name`。`age={20}` 变成 `props.age`。Props 是只读的——子组件绝不能给 `props` 的任意属性重新赋值。数据单向流动：从父到子，绝不反向。

Destructuring makes the syntax cleaner:

解构让语法更干净：

```jsx
function Child({ name, age }) {
  return (
    <p>
      {name} is {age} years old.
    </p>
  );
}
```

### 4.3 Props Are Not State / Props 不是状态

A common beginner misconception: changing a prop triggers a re-render in the child. This is both true and misleading. When the _parent_ re-renders and passes a new prop value, the child re-renders with the new value. But the child cannot change its own props. If the child needs to modify data that came from a parent, it cannot — it must ask the parent to do it. This is where the true architecture of React applications begins to take shape.

一个常见的新手误解：改变一个 prop 会触发子组件重渲染。这既正确又具有误导性。当*父组件*重渲染并传递新的 prop 值时，子组件带着新值重渲染。但子组件不能改变自己的 props。如果子组件需要修改来自父组件的数据，它不能——它必须请求父组件来做。React 应用的真正架构正是从这里开始成形的。

### 4.4 Lifting State Up / 状态提升

Suppose two sibling components need to share data. `SearchBar` captures the user's query. `SearchResults` displays the matching items. Neither can pass data to the other directly — siblings have no communication channel in React. The solution: move the shared state up to the nearest common ancestor, and pass it down to both children as props. This is called **lifting state up**.

假设两个兄弟组件需要共享数据。`SearchBar` 捕获用户的查询。`SearchResults` 显示匹配的条目。两者都不能直接向对方传递数据——React 中兄弟组件没有通信管道。解决方案：将共享状态上移到最近的公共祖先，然后通过 props 向下传递给两个子组件。这叫做**状态提升**。

```jsx
// The shared parent holds the state
// 共享的父组件持有状态
function SearchPage() {
  const [query, setQuery] = useState("");

  return (
    <div>
      <SearchBar query={query} onQueryChange={setQuery} />
      <SearchResults query={query} />
    </div>
  );
}

// Child receives both data and a way to change it
// 子组件接收数据以及改变它的方法
function SearchBar({ query, onQueryChange }) {
  return (
    <input
      type="text"
      value={query}
      onChange={(e) => onQueryChange(e.target.value)}
    />
  );
}
```

The parent owns the state. One child displays it. The other child changes it. The parent passes down not just data, but also the function to update it. This pattern — data down, actions up — is the backbone of React architecture. It scales from a two-component search bar to a multi-page application.

父组件持有状态。一个子组件显示它。另一个子组件改变它。父组件不仅向下传递数据，还传递更新它的函数。这种模式——数据向下，操作向上——是 React 架构的主心骨。它从两个组件的搜索栏扩展到多页面应用。

### 4.5 How I Learned Props / 我是怎么学会 Props 的

I first encountered props in my blog's `App.jsx` — components like `<Header />` and `<Footer />` stood alone without props, while `<PostPage>` received `id` from the URL via `useParams`, not props. The first genuine prop pattern I wrote was when extracting the `Lightbox` component. The `Lightbox` needed to know which images to display, which one was currently shown, and what to do when the user pressed "next" or "previous". The `PhotographyPage` held all that information. The LLM suggested extracting `Lightbox` to its own file and passing `images`, `currentIndex`, `onClose`, `onPrev`, `onNext` as props. At the time, I thought of props as "the things you put on the JSX tag when the LLM tells you to." Only later, when I needed to reuse `Lightbox` on a different page with different images, did the design click: the parent knows _what_. The child knows _how to show it_. Props are the contract between them.

我第一次遇到 props 是在我博客的 `App.jsx` 里——像 `<Header />` 和 `<Footer />` 这样的组件没有 props 独立存在，而 `<PostPage>` 通过 `useParams` 从 URL 接收 `id`，不是通过 props。我写的第一个真正的 prop 模式是在提取 `Lightbox` 组件的时候。`Lightbox` 需要知道要显示哪些图片、当前显示哪一张、以及用户按下“上一张”或“下一张”时该做什么。`PhotographyPage` 持有所有这些信息。大模型建议把 `Lightbox` 提取到自己的文件，并把 `images`、`currentIndex`、`onClose`、`onPrev`、`onNext` 作为 props 传递。当时，我把 props 当作“大模型让你放在 JSX 标签上的那些东西”。后来，当我需要在另一个有不同图片的页面上复用 `Lightbox` 时，这个设计才通了：父组件知道*什么*。子组件知道*如何展示它*。Props 是它们之间的契约。

## 5. Side Effects: useEffect / 副作用：useEffect

### 5.1 What Is a Side Effect? / 什么是副作用？

A React component's primary job is to return JSX. Given some props and state, it computes what the UI should look like. This computation should be **pure** — calling it multiple times with the same inputs should produce the same output, without affecting anything outside the function.

React 组件的主要工作是返回 JSX。给定一些 props 和状态，它计算出 UI 应该长什么样。这个计算应该是**纯粹的**——用相同的输入多次调用它应该产生相同的输出，且不影响函数外部的任何东西。

But real applications need to do impure things. They need to fetch data from a server. They need to set timers. They need to subscribe to browser events. They need to modify the DOM directly when React's model falls short. These impure operations are called **side effects**, and they belong inside `useEffect`.

但真实应用需要做不纯的事。它们需要从服务器获取数据。它们需要设置定时器。它们需要订阅浏览器事件。它们需要在 React 模型不足时直接修改 DOM。这些不纯的操作被称为**副作用**，它们属于 `useEffect` 内部。

### 5.2 The Basic Syntax / 基本语法

`useEffect` takes two arguments: a function to run, and an array of dependencies. The function contains the side effect code. The dependency array tells React _when_ to re-run the effect.

`useEffect` 接受两个参数：一个要运行的函数，和一个依赖数组。函数包含副作用代码。依赖数组告诉 React *何时*重新运行该 effect。

```jsx
import { useEffect } from "react";

function PostPage({ postId }) {
  const [post, setPost] = useState(null);

  useEffect(() => {
    // This runs after React commits the component to the DOM
    // 这会在 React 将组件提交到 DOM 之后运行
    fetch(`/api/posts/${postId}`)
      .then((res) => res.json())
      .then((data) => setPost(data));
  }, [postId]); // Re-run whenever postId changes
  // postId 改变时重新运行

  // ...
}
```

The dependency array is not an afterthought. It is the core contract of `useEffect`. If you omit it, the effect runs after every render. If you provide an empty array `[]`, the effect runs once, after the first render. If you list specific dependencies, the effect runs after the first render and whenever any dependency changes. A missing dependency is a bug — the effect will see stale values. An extra dependency causes unnecessary re-execution. Getting the dependency array right is the single hardest part of `useEffect`, and the React compiler will warn you about it with lint rules.

依赖数组不是事后补充。它是 `useEffect` 的核心契约。如果你省略它，effect 在每次渲染后运行。如果你提供空数组 `[]`，effect 在首次渲染后运行一次。如果你列出特定依赖，effect 在首次渲染后以及任何依赖改变时运行。遗漏依赖是一个 bug——effect 会看到过时的值。多余的依赖导致不必要的重新执行。把依赖数组写对是 `useEffect` 最难的部分，React 编译器会通过 lint 规则警告你。

### 5.3 Data Fetching: The Most Common Side Effect / 数据请求：最常见的副作用

The most frequent use of `useEffect` is fetching data from an API. My blog's `PostPage` does exactly this. When the page loads, it fires off several requests in parallel — the post body, the like status, the likes list, the comments — each in its own `authFetch` call inside `useEffect`.

`useEffect` 最常见的用途是从 API 获取数据。我博客的 `PostPage` 正是这样做的。当页面加载时，它并行发出多个请求——帖子正文、点赞状态、点赞列表、评论——每个都在 `useEffect` 里的独立 `authFetch` 调用中。

```jsx
// From my blog's PostPage.jsx — simplified
useEffect(() => {
  authFetch(`/api/posts/${id}/like_status`)
    .then((r) => r.json())
    .then((res) => setIsLiked(res?.data?.liked || false));

  authFetch(`/api/posts/${id}/likes`)
    .then((r) => r.json())
    .then((res) => setLikesUsers(res.data || []));

  getComments(id).then((res) => setComments(res.data || res || []));
}, [id]);
```

This pattern is so common that it feels automatic: put the URL in the effect, parse the JSON, set the state. But there is a pitfall here that I did not understand until it caused a real bug — and it is precisely the bug that damaged my blog's like data in its earliest version.

这个模式如此常见，以至于感觉是自动的：把 URL 放进 effect，解析 JSON，设置状态。但这里有一个坑，直到它导致了一个真实的 bug 我才理解——而它恰恰是最早版本中损坏了我博客点赞数据的那个 bug。

### 5.4 The Bug That Taught Me Everything / 那个教会我一切的 Bug

In the earliest version of my blog, the like button's event handler did not wait for the server response before updating the UI. The code (which I no longer have the exact source for) followed this disastrous sequence:

在我博客最早的版本中，点赞按钮的事件处理器在更新 UI 之前没有等待服务器响应。代码（我已没有确切源码）遵循了这样灾难性的序列：

```
User clicks like
↓
Frontend immediately toggles isLiked = true and increments likes_count
↓
A fetch request is sent to the backend... at some point
↓
If the request fails? Too late — the UI already changed.
```

The result: a user could click like, see the heart turn red, but the network request might fail silently. If they then clicked again to unlike, and _that_ request succeeded, the backend would decrement the like count — even though the like was never actually recorded. The net effect was a negative like count and corrupted data.

结果：用户点赞，看到爱心变红，但网络请求可能静默失败。如果他们再点一次取消点赞，而*那次*请求成功了，后端会递减点赞数——尽管那个赞从未真正记录过。净效应是负的点赞数和损坏的数据。

The fix was to make the event handler `async` and `await` the server response before touching any state. The UI update moved to _after_ the confirmation.

修复是把事件处理器变成 `async`，在触碰任何状态之前 `await` 服务器响应。UI 更新移到确认*之后*。

```jsx
// Fixed version — the UI waits for the server
const handleLike = async () => {
  try {
    const res = await authFetch(`/api/posts/${id}/like`, {
      method: "POST",
    });
    const data = await res.json();
    if (data?.data) {
      setPost({ ...post, likes_count: data.data.likes_count });
      setIsLiked(data.data.liked);
    }
  } catch (error) {
    // Request failed — UI stays unchanged
  }
};
```

The lesson is not about `async/await` syntax. The lesson is about where trust lives. The UI must never assume a side effect succeeded. The server is the source of truth. The frontend is a mirror. An effect that updates state based on an external operation must always wait for the operation to complete and must always check the result before committing to the state change. This applies to `fetch` in event handlers, `fetch` in `useEffect`, `localStorage.setItem`, and any other interaction with the outside world.

教训不在于 `async/await` 语法。教训在于信任住在哪里。UI 绝不应假设副作用成功了。服务器是真相的来源。前端是一面镜子。基于外部操作更新状态的 effect 必须永远等待操作完成，并且必须在提交状态变更之前检查结果。这适用于事件处理器中的 `fetch`、`useEffect` 中的 `fetch`、`localStorage.setItem`，以及与外部世界的任何其他交互。

### 5.5 Cleanup: The Most Overlooked Part / 清理函数：最被忽视的部分

Some side effects set up ongoing subscriptions — timers, event listeners, WebSocket connections. These must be torn down when the component unmounts, or when the effect re-runs due to a dependency change. If not, they accumulate, causing memory leaks and phantom interactions.

有些副作用会设置持续性订阅——定时器、事件监听器、WebSocket 连接。这些必须在组件卸载时，或 effect 因依赖变更而重新运行时被拆除。否则它们会累积，导致内存泄漏和幽灵般的交互。

`useEffect` supports this through a **cleanup function**. Return a function from the effect, and React will call it before the next run of the effect (or when the component unmounts). This is not an optional feature — it is part of the contract.

`useEffect` 通过**清理函数**支持这一点。从 effect 中返回一个函数，React 会在下次 effect 运行前（或组件卸载时）调用它。这不是可选功能——它是契约的一部分。

```jsx
useEffect(() => {
  // Set up a subscription
  const timer = setInterval(() => {
    console.log("tick");
  }, 1000);

  // Return a cleanup function
  return () => {
    clearInterval(timer);
  };
}, []); // Empty deps: set up once, clean up once on unmount
```

My blog's `Header` component uses this pattern for polling unread message counts. It sets up a 30-second interval. If the user navigates to a different page while the interval is running, the cleanup function clears it, preventing a stale timer from trying to update a component that no longer exists.

我博客的 `Header` 组件用这个模式来轮询未读消息计数。它设置了一个 30 秒的间隔。如果用户在间隔运行期间导航到另一个页面，清理函数会清除它，防止一个过期的定时器尝试更新一个不再存在的组件。

### 5.6 The Dependency Array and Stale Closures / 依赖数组与过期闭包

The dependency array is the single most common source of `useEffect` bugs. An effect closes over the variables from its render. If a variable is used inside the effect but not listed in the dependency array, the effect will see a stale value from an old render — a bug that is hard to spot and harder to debug.

依赖数组是 `useEffect` bug 最常见的来源。一个 effect 闭包了它所在渲染的变量。如果一个变量在 effect 内部被使用但没有列在依赖数组中，effect 将看到一个来自旧渲染的过期值——这是难以发现、更难调试的 bug。

```jsx
// Bug: count is used but not listed as a dependency
useEffect(() => {
  document.title = `Count: ${count}`;
}, []); // count never updates — title always shows initial value

// Correct: count is a dependency
useEffect(() => {
  document.title = `Count: ${count}`;
}, [count]);
```

The React linter rule `react-hooks/exhaustive-deps` catches this. Always include every variable from the component scope that the effect reads. If a value should not trigger a re-run, ask yourself why the effect needs it — the answer often reveals a design issue.

React 的 lint 规则 `react-hooks/exhaustive-deps` 会捕获这个。始终包括 effect 读取的组件作用域内的每个变量。如果某个值不应该触发重新运行，问自己为什么 effect 需要它——答案往往揭示一个设计问题。

### 5.7 How I Learned useEffect / 我是怎么学会 useEffect 的

I did not learn `useEffect` by studying its API. I saw it in generated code, always wrapping `authFetch` calls. I treated it as "the place where fetch calls go." The dependency array was `[id]` because the LLM put `[id]` there. I did not question it.

我不是通过研究它的 API 学会 `useEffect` 的。我在生成的代码中看到它，总是包裹着 `authFetch` 调用。我把它当作“放 fetch 调用的地方”。依赖数组是 `[id]` 因为大模型在那里放了 `[id]`。我没有质疑它。

The turning point came when I needed to add polling — an interval that checked for new messages every 30 seconds. The LLM generated a `setInterval` inside `useEffect` with a cleanup function that called `clearInterval`. When I forgot the cleanup function in a different component, the timer kept running after the component was gone, and console errors started appearing. That forced me to understand the cleanup lifecycle. Later, when I tried to add a dependency to an effect and saw the linter complain, I learned about the dependency array contract.

转折点出现在我需要添加轮询的时候——一个每 30 秒检查新消息的间隔。大模型在 `useEffect` 里生成了一个 `setInterval`，带着调用 `clearInterval` 的清理函数。当我在另一个组件里忘了清理函数时，定时器在组件消失后继续运行，控制台开始出现错误。这迫使我理解了清理生命周期。后来，当我试图给一个 effect 添加依赖而看到 linter 抱怨时，我学到了依赖数组契约。

`useEffect` is the most conceptually dense hook in React. It bundles together data fetching, subscription management, and lifecycle coordination into a single API. Most hooks have one job. `useEffect` has three. It is the one hook where a shallow understanding — "the place for fetch calls" — can get you surprisingly far, until it suddenly doesn't. When it stops working, the answer is almost always in one of three places: a missing dependency, a missing cleanup, or a missing check on the result of an async operation.

`useEffect` 是 React 中概念密度最高的 hook。它把数据请求、订阅管理和生命周期协调打包进了单一 API。大多数 hook 只有一个职责。`useEffect` 有三个。它是那种浅层理解——“放 fetch 调用的地方”——可以让你惊人地走得很远，直到它突然失效的 hook。当它停止工作时，答案几乎总是在三个地方之一：遗漏的依赖、遗漏的清理函数，或者对异步操作结果遗漏的检查。

## 6. Global State: useContext / 全局状态：useContext

### 6.1 The Problem Props Cannot Solve / Props 解决不了的问题

Props work beautifully when data flows straight down from parent to child. But real component trees are rarely one level deep. A piece of state that is needed by many components scattered across the tree — the current user, the UI theme, the selected language — must be passed down through every intermediate component, even those that do not use it. This pattern is called **prop drilling**: threading data through components that merely forward it, like a bucket brigade where half the participants do nothing but pass the bucket.

当数据从父组件直下到子组件时，props 工作得很漂亮。但真实的组件树很少只有一层。一个被树中散落各处的许多组件需要的状态——当前用户、UI 主题、选择的语言——必须经过每个中间组件向下传递，即使那些组件根本不用它。这种模式叫做**prop 钻孔**：将数据穿过那些仅仅转发它的组件，就像一场传递水桶的接力，其中一半参与者除了传桶什么都不做。

Prop drilling is not a bug. For shallow trees, it keeps data flow explicit and easy to trace. But as an application grows, it becomes noise. A component that takes a `theme` prop only to pass it straight to its children is declaring a dependency it does not actually have. The code becomes harder to read, harder to refactor, and harder to type. React's solution to this is **Context** — a way to broadcast data to the entire subtree without threading it through every intermediate layer.

Prop 钻孔不是一个 bug。对浅层树来说，它使数据流显式且易于追踪。但随着应用增长，它会变成噪音。一个接收 `theme` prop 只为直接传给它孩子的组件，正在声明一个它实际并不需要的依赖。代码变得更难阅读、更难重构、更难以打字。React 对此的解决方案是 **Context**——一种将数据广播到整个子树而无需穿过每个中间层的方式。

### 6.2 Creating and Using Context / 创建和使用 Context

Context works in three steps. First, create the context object. Second, wrap a subtree in a **Provider** and give it a value. Third, any component inside that subtree can read the value with `useContext`.

Context 工作分三步。第一，创建 context 对象。第二，用一个 **Provider** 包裹一个子树并给它一个值。第三，该子树内任何组件都可以用 `useContext` 读取这个值。

```jsx
import { createContext, useContext, useState } from 'react';

// Step 1: Create the context
// 第一步：创建 context
const ThemeContext = createContext(null);

// Step 2: Provide the value somewhere high in the tree
// 第二步：在树的高处提供值
function App() {
  const [theme, setTheme] = useState('light');

  return (
    <ThemeContext.Provider value={{ theme, setTheme }}>
      <Header />
      <Main />
      <Footer />
    </ThemeContext.Provider>
  );
}

// Step 3: Consume the value anywhere below
// 第三步：在下方任意处消费值
function Header() {
  const { theme, setTheme } = useContext(ThemeContext);
  return (
    <button onClick={() => setTheme(theme === 'light' ? 'dark' : 'light')}>
      Current theme: {theme}
    </button>
  );
}
```

The Provider is a component. Anything you pass as `value` becomes available to every descendant. The value can be anything — a number, a string, an object, a function. When the value changes, every component that reads it re-renders. This is the core tradeoff of Context: it is powerful precisely because it affects many components at once, and it must be used carefully for exactly the same reason.

Provider 是一个组件。你作为 `value` 传递的任何东西对每个后代都变得可用。值可以是任何东西——数字、字符串、对象、函数。当值改变时，每个读取它的组件都会重渲染。这是 Context 的核心权衡：它强大恰恰因为它同时影响许多组件，而它必须小心使用也正是出于同样的原因。

### 6.3 A Real Example: Dark Mode in My Blog / 一个真实案例：我博客的暗色模式

My blog supports a dark mode toggle. The current theme — `light` or `dark` — is needed by nearly every visual component to choose the right CSS class. Passing `darkMode` as a prop through the entire component tree would mean adding it to `App`, `Header`, `Footer`, `PostPage`, `PhotographyPage`, `Sidebar`, and every other page and subcomponent. Most of those components do nothing with the theme except pass it further down. This is a textbook case for Context.

我的博客支持暗色模式切换。当前主题——`light` 或 `dark`——几乎被每个视觉组件需要以选择正确的 CSS 类。将 `darkMode` 作为 prop 穿过整个组件树意味着要把它加到 `App`、`Header`、`Footer`、`PostPage`、`PhotographyPage`、`Sidebar` 以及每个其他页面和子组件上。这些组件中大多数除了继续向下传递之外什么也不对主题做。这是 Context 的教科书式用例。

The implementation uses a pattern that is worth studying because it encapsulates the Context logic into a single custom hook, hiding the raw `useContext` call from the rest of the codebase. A file called `ThemeContext.jsx` exports two things: the `ThemeProvider` component and a `useTheme` hook.

这个实现使用了一个值得研究的模式，因为它将 Context 逻辑封装进一个自定义 hook，对代码库其余部分隐藏了原始的 `useContext` 调用。一个叫 `ThemeContext.jsx` 的文件导出两样东西：`ThemeProvider` 组件和一个 `useTheme` hook。

```jsx
// ThemeContext.jsx (simplified from my blog)
import { createContext, useContext, useState, useEffect } from 'react';

const ThemeContext = createContext(null);

export function ThemeProvider({ children }) {
  const [darkMode, setDarkMode] = useState(() => {
    // Check system preference on first load
    // 首次加载时检查系统偏好
    return window.matchMedia('(prefers-color-scheme: dark)').matches;
  });

  useEffect(() => {
    // Apply theme class to <html> for CSS variable switching
    // 将主题类应用到 <html> 以切换 CSS 变量
    document.documentElement.classList.toggle('dark-mode', darkMode);
  }, [darkMode]);

  return (
    <ThemeContext.Provider value={{ darkMode, setDarkMode }}>
      {children}
    </ThemeContext.Provider>
  );
}

export function useTheme() {
  const context = useContext(ThemeContext);
  if (!context) {
    throw new Error('useTheme must be used within a ThemeProvider');
  }
  return context;
}
```

Then, in `App.jsx`, the entire application is wrapped once:

然后，在 `App.jsx` 中，整个应用被包裹一次：

```jsx
<ThemeProvider>
  <Header />
  <Routes />
  <Footer />
</ThemeProvider>
```

And any component that needs the theme calls the hook:

任何需要主题的组件调用这个 hook：

```jsx
function Header() {
  const { darkMode, setDarkMode } = useTheme();
  return (
    <button onClick={() => setDarkMode(!darkMode)}>
      {darkMode ? '☀️' : '🌙'}
    </button>
  );
}
```

The encapsulation matters. Raw `useContext(ThemeContext)` works, but the custom `useTheme` hook does three things: it gives the operation a readable name, it throws a clear error if the Provider is missing, and it makes refactoring easier because the Context object itself stays private to the file. This is a pattern worth adopting from the start.

封装很重要。原始的 `useContext(ThemeContext)` 能工作，但自定义 `useTheme` hook 做了三件事：给操作一个可读的名字，如果 Provider 缺失则抛出一个清晰的错误，并且让重构更容易因为 Context 对象本身保持对文件的私有。这是一个值得从一开始就采用的模式。

### 6.4 When Not to Use Context / 什么时候不要用 Context

Context is not a replacement for all prop passing. It solves a specific problem: data that is genuinely needed by many components at different nesting levels. Using Context for data that only two components share is overengineering — lift the state up and pass it as props instead. The explicit data flow of props is easier to debug and easier to reason about.

Context 不是所有 prop 传递的替代品。它解决一个特定的问题：被不同嵌套层级的许多组件真正需要的数据。为只有两个组件共享的数据使用 Context 是过度工程——将状态提升并通过 props 传递即可。Props 的显式数据流更容易调试、更容易推理。

A second pitfall is performance. When the value of a Context changes, *every* component that reads that Context re-renders. If the Context value is a large object and many components only need a small part of it, re-rendering them all on every change is wasteful. This is why libraries like Redux and Zustand exist — they offer fine-grained subscriptions that Context alone does not provide. For a blog of my size, a single `ThemeContext` with a boolean value is perfectly appropriate. For a large application with frequently changing shared state, consider splitting Contexts by concern or reaching for a dedicated state management library.

第二个陷阱是性能。当 Context 的值改变时，*每个*读取该 Context 的组件都会重渲染。如果 Context 值是一个大对象而许多组件只需要其中一小部分，每次变化都重渲染它们全体是浪费的。这就是 Redux 和 Zustand 这类库存在的原因——它们提供细粒度的订阅，而单独的 Context 做不到。对于我博客这种规模，一个带布尔值的 `ThemeContext` 完全合适。对于频繁变化的共享状态的大型应用，考虑按关注点拆分 Context 或使用专门的状态管理库。

### 6.5 How I Learned Context / 我是怎么学会 Context 的

I first encountered Context not through a tutorial, but through a generated file called `ThemeContext.jsx` that appeared in my blog project. It exported a `useTheme` hook that returned `{ darkMode }`. I used it exactly as the LLM instructed — `const { darkMode } = useTheme()` — without understanding what happened behind the call. It felt like magic. A variable appeared in my component with no prop and no import beyond the hook. I could toggle a switch in the header, and the entire page changed color.

我第一次遇到 Context 不是通过教程，而是通过我博客项目中一个叫 `ThemeContext.jsx` 的生成文件。它导出一个返回 `{ darkMode }` 的 `useTheme` hook。我完全按照大模型的指示使用它——`const { darkMode } = useTheme()`——却不理解调用背后发生了什么。它感觉像魔法。一个变量出现在我的组件中，没有 prop，除了 hook 没有导入。我可以在 header 里拨动一个开关，整个页面改变颜色。

The magic started to make sense only when I broke it. At one point, I tried to use `useTheme` in a component that was *not* wrapped by `<ThemeProvider>`. The hook threw an error: "useTheme must be used within a ThemeProvider." The error message taught me the architecture: the Provider at the top of the tree owns the state. The hook is just a reader. Without the Provider, there is nothing to read. This is the same lesson as props, transposed to a global scale: the data still has a single owner. Context does not create data — it broadcasts it.

魔法在我打破它时才开始变得有意义。有一次，我试图在一个*没有*被 `<ThemeProvider>` 包裹的组件中使用 `useTheme`。这个 hook 抛出了一个错误："useTheme must be used within a ThemeProvider"。这条错误消息教给了我架构：树顶部的 Provider 持有状态。Hook 只是一个读取器。没有 Provider，就没有东西可读。这和 props 是同一课，只是移到了全局尺度：数据仍然有单一的所有者。Context 不创造数据——它广播数据。

Later, when I added the CSS conflict resolution — moving all theme-related overrides into `.dark-mode` class toggles in `index.css` instead of inline styles — I finally understood the full design. The `ThemeProvider` does not just hold a boolean. It synchronizes that boolean with a DOM class on `<html>`, and the CSS layer responds. The React state is the source of truth. The DOM is a reflection. Context is the conduit. Every piece of the dark mode feature — React state, Context, the `useTheme` hook, the `useEffect` that toggles the class, the CSS rules — suddenly formed a coherent picture. None of it made sense in isolation. Together, it was a miniature masterclass in React architecture, and I had built it without understanding it. The understanding came later, when the pieces I had assembled by vibe finally clicked into place.

后来，当我解决了 CSS 冲突——将所有与主题相关的覆盖移到 `index.css` 中的 `.dark-mode` 类切换而不是内联样式——我终于理解了完整的设计。`ThemeProvider` 不只是持有一个布尔值。它将那个布尔值与 `<html>` 上的一个 DOM 类同步，CSS 层响应。React 状态是真源。DOM 是镜像。Context 是导管。暗色模式功能的每一片——React 状态、Context、`useTheme` hook、切换类的 `useEffect`、CSS 规则——突然形成了一幅连贯的图景。单独看哪一块都没有意义。合在一起，它是一堂微型 React 架构大师课，而我在不理解它的情况下把它建了出来。理解是后来才来的，当我靠 vibe 组装起来的那些碎片终于拼到一起。

---

This concludes the six core concepts of React. JSX is JavaScript in disguise. Components are functions that return it. State makes them remember. Props make them talk. Effects connect them to the outside world. Context lets them share without shouting through the entire family tree. These six ideas — understood not just as APIs but as design choices — are what turn React from a set of incantations into a tool you can reason about.

至此，React 的六个核心概念结束。JSX 是伪装的 JavaScript。组件是返回它的函数。State 让它们记忆。Props 让它们交谈。Effects 将它们连接到外部世界。Context 让它们无需吼穿整个家族树就能共享。这六个思想——不仅作为 API 理解，而且作为设计选择理解——正是将 React 从一套咒语变成你可以推理的工具的东西。
